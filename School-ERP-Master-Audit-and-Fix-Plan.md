## Verdict in one paragraph

The school vertical is broad and real: 34 `/school/*` routes, 33 school screens, a 10,637-line `school_service.dart` and a 5,615-line `school_export_service.dart` (72 export methods). The happy paths of admissions, attendance, marks, report cards, fee collection, library issue/return, payroll runs, discipline and alumni genuinely work against Supabase tables — and, since the dashboard deep-dives were written, the Teacher dashboard has become the first feature in the whole program to earn **Deep**: its fake KPIs, fallback schedule, Room 201 and missing Reports link are all fixed, with 4 real charts and real Excel. But depth is uneven in a specific, repeatable way: **edge cases are where the system stops**. Cheque bounce, demand lock, month close, RTE, marks lock, re-evaluation, GPS, meal plans, Excel import, notification delivery and real RAG are absent or label-only; several screens persist nothing (examinations, lesson plans) or persist into the wrong table (`school_circulars` as a shadow database — now also the audit-log viewer, the settings store, the gate-pass store and the AI draft store); and empty tables are routinely masked by invented demo data — including a fabricated medical profile (blood group B+, policy `#SHIV-MED-2026`), invented payroll staff with a fake bank account and PAN, invented "live GPS" values, and a fabricated parent-health card (height 165.0, weight 58.0, BMI 21.3). Count of ratings across all **80 deep-dived features: Deep 1 · Adequate 29 · Shallow 36 · Shell-only 14.** The Teacher dashboard is the only Deep; everything else has at least one missing edge case, one unwired enforcement, or one fake-data fallback.

## 0. How to Read

**Depth ratings (applied per feature, with evidence, never on impression).**

- **Deep** — full workflow including edge cases, verified live-data path from screen to table to report, no invented data on the path. One feature earns this: the Teacher dashboard (D1).
- **Adequate** — the happy path works end to end on real tables; edge cases are thin, or one secondary behaviour (a notification, a report, a config) is missing.
- **Shallow** — a screen exists and something works, but the workflow is incomplete, mostly display, or a critical step (persistence, approval, verification) is missing.
- **Shell-only** — a file, route or table exists, but it is barely functional, demo data, or label-only; using it in production would mislead the user.
- **Split ratings count as Shallow** in the totals (e.g. "Adequate (demands); lock Shell-only" counts as Shallow for the feature as a whole, because the "graph + Excel" / "workflow complete" standard is not met).

**Conventions used throughout.**

- `file:line` means the path inside the repo at `f627642`; `~` before a line number means located within a few lines of that number.
- "Grep-confirmed absence" means a stated pattern was searched across `lib/` (and `database/` where stated) and returned zero relevant hits. The pattern is quoted so the check can be repeated.
- "Fallback" means code that returns invented data when the real table is empty or errors. Every fallback quoted in this document is a verbatim value from the code. Fallbacks are the single most important cross-cutting finding (§C1): they make an empty system look populated.
- "In-memory" means data held in a Dart list that is lost on app restart. Any workflow whose only store is in-memory is not a workflow.
- "Circulars fallback" means a write that, on database failure, inserts its payload as JSON into `school_circulars` and returns success. The user sees "saved"; the record is unfindable in its own module.
- "Graph + Excel" is checked per report: both must be present and driven by real data. A chart rendering hard-coded numbers counts as **no graph**.
- "Role enforcement (one line)" is a single line per feature. It states what exists; Fix Pack B owns the fix.
- Money, dates and names in quoted fallbacks are the code's invented values, not real school data. The invented PAN/bank details are reproduced because they are the defect (a fake financial identity inside payroll seed data), not because they identify a real person — no such person exists in the system.
- **"s"-prefix credential rule (a hard rule from the owner):** all school-side credentials/IDs start with `s`; HR payroll staff IDs follow the `shr01` pattern (s + hr + 01). No live account is ever silently renamed — the rename list must be shown to the owner first (Fix Pack B B0).
